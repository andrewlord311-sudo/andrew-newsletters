EffeTune

An effects chain for listening, not for making · browser, Mac, Windows, Android

What it is. A real-time audio effect processor aimed at people who listen hard. You route audio — a file, a streaming app, a browser tab, or a physical input — through a chain you build yourself: EQ, dynamics, reverb, saturation, tube-amp emulation, live visualisers. The README counts about 114 effects in 14 categories. It also does offline file processing and, more interestingly, acoustic measurement: it measures a room and generates the correction EQ for it.

Why it is for you. Everything this newsletter has sent you about music so far has been about making or reading it. This is the first thing for the listening, which is where most of the hours actually go. Two specific hooks. It can process a browser tab, so it sits in front of anything streamed rather than only in front of files — which is the way most listening now happens. And the room-correction measurement is the part worth your evening: a measured curve for the room you listen in is the single change that alters how a Mahler symphony sounds more than any amount of choosing a different recording, and it is the kind of thing normally locked behind a paid plugin suite.

To try it. Nothing to install for a first look: there is a hosted build at effetune.frieve.com, and the README offers it as an installable web app from the same URL. Build a three-effect chain, play something you know well through it, and then try the measurement if you have any kind of microphone to hand. Ten minutes for the first, an hour if you do the room properly. For the Windows PC where the music work happens there is a desktop build and a VST build on the releases page.

Risk. The soundest-looking thing here: created February 2025, so getting on for two years old, committed to today, 20 forks and only 11 open issues against 153 stars — a ratio that reads as real use rather than a spike. Three honest caveats. The licence is MIT by GitHub's reading of the repository, but the README names MIT only for the "DSP Library" and never states the application's own licence in text, so that is a mixed signal worth checking against LICENSE before you reuse any of it. Do not count on the iPad: the README recommends Chrome, lists Safari under "limited support", and never mentions iOS or iPadOS at all — so this is the Mac, the PC and the Android phone, not the iPad, whatever a web app would normally imply. And the README says nothing either way about telemetry or analytics. No account, key or subscription is mentioned anywhere; there is a Ko-fi link and nothing else.

Fermata

A music stand for your own library, served to every device in the house · Mac, then any tablet

What it is. A self-hosted sheet music server. You point it at a folder of scores and it gives back a browsable, searchable library with a PDF practice reader, interactive MusicXML and Guitar Pro rendering, and practice tooling on top: metronome, practice tracking, ear training, fretboard drills. Its own README calls it "the music-stand equivalent of Jellyfin or Calibre-Web", which is exactly the right comparison.

Why it is for you. You read scores, and scores accumulate as PDFs in folders where nothing can find them. This is the first thing this newsletter has found that treats a personal score collection as a library to be served rather than a pile to be opened one file at a time — searchable, on a stand, in the room where the instrument is. The guitar side is not incidental either: Guitar Pro files, a fretboard drill and tab rendering all point at the guitar writing you have said you want to get back to, and the lute repertoire lives in the same formats. There is also a REST API and an optional MCP server, switched off by default — so once it holds your library it is scriptable, which is the version of this you would actually end up building yourself.

To try it. This one is the Mac for an evening, not a browser tab. The quick start is git clone, make a library and a config folder, drop some scores in, and docker compose up --build -d; then open localhost:8080. There is a pip-and-npm development path if you would rather not use Docker at all. Once it is up the README describes it as for "any device on your network" and names tablets on a stand, so reading it on the iPad is the intended use — served from the Mac, not from the NAS, which cannot run Docker. Budget an hour, most of it waiting for a build.

Risk. MIT, confirmed, and it is the thinnest project in this issue by a distance: 40 stars but only 2 forks, 16 open issues, created 19 August 2026, last pushed 25 October. It reads as one person's project, and two forks means almost nobody else has touched the code. Be clear-eyed about one thing in particular, to the author's credit, because he counted it himself in the README: the PDF-to-MusicXML transcription is rough — on his own 297-PDF library, only 6 of 293 transcribed scores had every bar adding up and 243 came back with low rhythm confidence. So treat the transcription as an experiment and the library-plus-reader as the actual product; the reader does not depend on it. The roadmap admits tuplets, grace notes and instrument-aware transcription are not done, and that it assumes six-string standard tuning. Nothing pipes into a shell, no account, no key, no cloud service — SQLite in a single container. Telemetry is not mentioned either way, and the README tells you to read the deployment guide before deciding whether it belongs on your home network, which is fair warning rather than a red flag.

Claudian

Claude Code, living inside Obsidian · Mac (desktop only)

What it is. An Obsidian plugin that embeds coding agents — Claude Code among them — directly in the vault, with the vault as the agent's working directory. Inline editing with a word-level diff preview, projects with a memory file the agent keeps updated, slash commands, @-mentions, and MCP server support.

Why it is for you. You already run Claude Code against the vault from a terminal. This removes the terminal: the agent works where the notes are, and the diff preview means you see what it proposes to change to a note before it changes it, which is the part the command line does worst. The projects-with-a-memory-file idea is worth a look on its own even if you never install it, because it is the same problem your own context files solve and a different answer to it. It is also the most established thing in this issue by the numbers.

To try it. Easiest route is Obsidian itself: Settings → Community plugins, search for Claudian, install, enable. It needs Obsidian 1.13 or later and at least one agent harness already installed, which you have. There is a build-from-source path (git clone into the plugins folder, npm install, npm run build) if you want to read the code first. Half an hour to have it running on something.

Risk. MIT, 15,908 stars, 1,086 forks and 72 open issues, created 5 December 2025 and pushed yesterday. On the star question: a 7% fork-to-star ratio and 72 live issues is what genuine use looks like, so the big number here is not the usual problem — but it is a big number, so read the issues before you trust it with anything. The real caution is what it can do, not who wrote it. The agent gets read, write, edit, search and shell access inside the vault, and the README does not describe any sandboxing or per-action permission prompt — the diff preview covers inline edits, not everything else. Point it at a vault whose backup you have just confirmed is current, and do that before the first run rather than after. Credentials: it needs a harness plus "a compatible subscription or API provider", and the troubleshooting notes imply it uses the CLI's own login rather than wanting a separate key. On data, the README is unusually specific and worth the credit: no telemetry beacons, no unsolicited background activity, network limited to the provider you configure, any MCP endpoints you add, and a listener bound to 127.0.0.1. Two limits: desktop only, so the iPad is out, and the Plugin API is labelled experimental.

For your projects

Promoted off the radar, where it sat last week for want of room. Something to use and something to learn from.

spectrometry_public

The Python and ffmpeg engines behind a science-video channel · Mac

What it is. The open-source code behind the spectrometry.mp4 videos: a set of independent Python engines that render frames which ffmpeg then turns into film. Fluid simulation, electric field lines, particle swarms, bouncing shapes, strange attractors, an oscilloscope, a simulated CRT, and molecular spectra. Each engine has its own CLI with named presets you invoke by name.

Why it is for you. This is the same architecture as your own video pipeline — deterministic scene, rendered to frames, handed to ffmpeg — with one difference worth stealing: yours records HTML scenes through a browser, this computes frames in Python. For anything with physics in it, numerical simulation, field lines, a spectrum, the Python route gives you per-frame control a recorded browser scene cannot, and the two can live in the same pipeline because they both end at ffmpeg. Use it for the explanatory material in your own field, where the visual vocabulary is exactly this: field lines, spectra, a CRT trace. Learn from it for the shape of the thing — one engine per effect, its own virtual environment, a catalogue of named presets rather than parameters you must remember. That last pattern is the one your pipeline would benefit from most.

To try it. git clone, a virtual environment, then pip install -r the requirements for one engine and run its cli.py list to see the presets, then render one with --preview for a quick small version. Needs Python 3.10 or newer and ffmpeg on the PATH. GPU is optional — the NVIDIA path (CuPy, NVENC) is a fall-through, and it runs on a plain CPU, which is what makes it usable on a Mac at all, unlike most of this genre. An hour, and use a separate virtual environment per engine as the README insists.

Risk. MIT, confirmed, 57 stars, 7 forks, 1 open issue, created 11 June 2026 and last pushed 24 October — so active, but not touched for a fortnight. Small and essentially one person's work. No account, no key, no paid service anywhere; the only external links are the author's own channels. Four things to know before you commit an evening. Output is vertical 1080×1920 by default — configurable, and convenient if the short-form clips are what you want, inconvenient otherwise. The only performance figures given are rough ratios measured on one NVIDIA machine, so you do not know what a render costs on your hardware until you try one. Apple Silicon is never mentioned. And the author asks, beyond the licence, for a credit in your README or video description, and states plainly that the spectra are simulations rather than measurements — which matters if anything built from it ever claims to show real data. Some engines in the catalogue are not released yet.

A game

Held over from a fortnight ago, when there was already a game in the issue. The ratings say keep the game, so here it is.

Claude of Tanks

Armoured combat in a browser tab, with touch controls · browser, phone, probably iPad

What it is. A tank combat simulator built from scratch in Three.js and Vite, hosted and playable with no install: 33 battlefields, 13 modes, and a fleet the README variously counts at 220, 222 and 279 vehicles. Not arcade-shaped underneath — plate-level armour, ballistics, modules and physics. Solo play is against bots; LAN and private rooms run peer-to-peer in the host's browser over WebRTC, and internet rooms use a small Cloudflare-style rooms Worker.

Why it is for you. The honest first reason is that it is ten seconds from a browser tab and genuinely good, which is what this section is for. The second is that it is built out of your own stack — Three.js and Vite, with a tiny Worker doing the matchmaking and WebRTC carrying the rest — so it doubles as a worked example of multiplayer without a server to run or pay for, which is the question that stops most small browser games before they start. And there is a third, drier reason: its provenance policy is the most rigorous thing in this issue, and if you ever ship a game with generated assets it is a model for how to keep that defensible.

To try it. Open cot.kevinliu.studio and play. The README claims "desktop or mobile" with complete touch controls and a safe-area layout, so a keyboard is not needed — which is what makes the iPad plausible, though no specific device is named as tested, so treat it as claimed rather than confirmed. To run it locally it is npm install then npx vite; no Node version is stated. No account, no key, no AI service at runtime — Claude and Codex were development tools, not dependencies. A restricted network may need a TURN relay for internet rooms.

Risk. Active and real: 529 stars, 110 forks, only 2 open issues, created 29 July 2026 and pushed today, with release gates and tests. The licence genuinely is mixed, and this is the thing to understand. MIT by default, but the author explicitly reserves the procedural vehicle and battlefield source, the fleet and map data, generated assets, authored media and branding as proprietary "Reserved Content"; earlier public revisions stay MIT. So: play it freely, read the engine code freely, and do not lift the fleet — check LICENSE and LICENSE-POLICY.md before reusing any file. On the provenance question, which matters for a game shaped like a commercial one: the README states every selectable vehicle model is original first-party work from the project's own pipeline, and that external models are kept only as quarantined research references never loaded as playable geometry. It does not say where the vehicle names come from. Nothing is said about analytics on the hosted build, and multiplayer necessarily means your browser talks to other players' browsers.
