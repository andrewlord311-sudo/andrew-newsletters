Try this weekend

Three corners of your range: the photo library, a score on a page, and a game small enough to finish.

PhotoMapAI

Search a huge photo library by describing the picture · Mac, in a browser

What it is. A local image browser and search tool built for collections that have outgrown folders. It runs CLIP over your photos so you can search by text or by similarity to another picture, and it clusters the whole library into a visual “semantic map” you can navigate. Around that: slideshows, albums, bookmarks, a metadata viewer, and a curator mode for assembling training sets. Video is handled by indexing one extracted still frame.

Why it is for you. The photo problem you actually have is not storage, it is that nothing can find anything: tens of thousands of images, no tags, and no intention of ever adding any. This is the version of the answer that needs no tagging at all — you type what the picture was and it goes and finds it. The semantic map matters for the other half of the job, culling: clusters are how you see that you took the same sunset forty times, which is the view a filename-sorted grid can never give you. And it is all on your machine, which for a personal library is the whole point.

To try it. There is a native installer: download the macOS .dmg from the releases page and drag it to Applications. Apple Silicon acceleration is automatic, so the Mac is the right machine for it. If you would rather keep it in Python, it is on PyPI for Python 3.11 to 3.14 (uv tool install photomapai --torch-backend auto, then start_photomap). Budget an evening, but mostly waiting: the first launch pulls down a multi-gigabyte set of libraries before it will index anything. Point it at one folder of a few thousand photos first rather than the whole library.

Risk. MIT by GitHub's reading of the repository, but the README contains no licence statement at all, so check LICENSE before you reuse any of it. The age and activity are the reassuring part — created August 2025, so fifteen months old, and pushed two days ago — but the shape is thin: 91 stars, 4 forks, zero open issues. That is one person's project with almost nobody else in the code, and zero open issues on a fifteen-month-old tool means either very few users or issues that are not being filed. On your data the README is clear and worth the credit: “All images are local to your computer; nothing goes out to the internet”, with no account, no key and no telemetry mentioned. Two honest gaps in that: the first launch plainly does reach the internet to fetch its libraries, and the README never says where the model weights come from. The web interface is described as responsive for desktop and mobile, but the iPad is never named, and the heavy lifting is happening on the Mac regardless. An NVIDIA GPU is used if one is present, which on your kit it is not; nothing says what indexing costs on Apple Silicon, so measure it on a small folder before committing the library.

astro-lilypond

Engraved notation on an Astro page, compiled at build time · your existing Astro project

What it is. An Astro integration that renders LilyPond notation to images while the site builds. You write the score inside Markdown or drop in an Astro component; it also ships a content loader that turns a folder of .ly files into an Astro content collection. Output is .svg, .png and .pdf, and it generates the alt text from the score's title and composer unless you give it your own.

Why it is for you. This is the first pick that sits inside the stack you already build in rather than beside it. Astro is your stack, and the one thing a music page always ends up needing — real engraved notation, not a screenshot of it — is the thing that normally forces a client-side renderer, a font payload and a layout that reflows badly on a phone. Compiling at build time with zero client-side JavaScript is the right answer to that: the page ships an image, so it is fast, it prints, and it reads correctly on the iPad without running anything. The content-collection loader is the part worth more than it looks: a directory of .ly files becomes a browsable, templatable score site, which is the shape of the hymn and teaching pages rather than a one-off example.

To try it. One line into an existing Astro project: npx astro add astro-lilypond. Then put a score in a Markdown file and build. Docs are at lilypond.ky.fyi. Half an hour if the LilyPond question below turns out the easy way, an evening if it does not.

Risk. MIT, 62 stars, 3 forks, one open issue, created July 2026 and pushed on 2 November. One person's project, four months old, and no version or stability claim anywhere — so treat it as something to try on a branch, not to put under a page you have already published. The one unresolved thing, and it decides whether this is half an hour or an evening: nothing in the README or the docs site says whether LilyPond itself has to be installed on the machine that builds the site. I checked the root manifest and there is no bundled WebAssembly LilyPond and no install script in it, but the project is a monorepo and the package's own manifest was not reachable, so this is genuinely unknown rather than quietly fine. Reason it through before you start: a project claiming “all LilyPond syntax” almost certainly shells out to the real LilyPond, which would mean installing it locally and having it available wherever the site builds. Worth knowing on that second point: the repo's own tooling includes wrangler, so the author deploys with Cloudflare — a hint, not a guarantee, that a Cloudflare build is a solved problem. Two plain limits: LilyPond input only — no ABC and no MusicXML, which is what you mostly have, so this is for scores you write in LilyPond or convert first; and no MIDI or audio, it renders pictures. No accounts, keys or telemetry are mentioned anywhere.

Playload

A whole game inside a URL · browser, ten seconds, nothing installed

What it is. A tiny game engine where the entire program lives in the link. You write JavaScript in a code editor beside the running game, press Run, and share the game by sending the URL. The specification caps a program at 3 KB of compressed JavaScript; input is four directions and two buttons; there is built-in 8×8 pixel artwork and emoji to draw with, and a sound syntax modelled on the old ZX PLAY command. A comment at the top of your code (// @title) names the browser tab and the bookmark.

Why it is for you. Two of your habits meet here. You make small web things and send them to people as links — and this is that, with no hosting, no build and no account anywhere in it: the game is the link. And you write games to teach the children, where the thing that kills a project is scope. A 3 KB ceiling and a two-button pad is the most useful constraint in this issue: it makes an evening's game finishable, and finishable is the only kind that ever gets played. Write a times-tables chase or a note-reading game after dinner, send the URL, done.

To try it. Open kitao.dev/playload/, run one of the examples, edit the code in the panel beside it and press Run. There is a “Play community games” link to see what others have fitted into 3 KB. Ten seconds to the first game, and bookmark the URL or you lose your work — the bookmark is the save file.

Risk. The youngest thing here by a distance: created 6 October, so 37 days old, just past the line this newsletter draws at 30. The numbers are small too — 103 stars, 4 forks — but the provenance is the reason it is a pick anyway: the author also wrote Pyxel, the retro game engine for Python at 18,605 stars, so this is a known hand working in a format they know, not an unknown quantity. Against that, the README is nearly empty: no install steps, no licence text, no maturity statement, no platform list. MIT is GitHub's reading of the repository, so check LICENSE if you mean to reuse the engine. Do not count on the iPad. Neither the repository nor the site names a single supported browser, device or touch control, and the input scheme is four directions and two buttons, which implies a keyboard — so tablet play is untested, not promised. The flip side of code-in-a-URL is that nothing is stored anywhere: no login, no server and no telemetry are mentioned, which is as private as software gets, and also means a lost bookmark is a lost game. Keep anything you care about in a file as well.

For your projects

For the video pipeline — the one area the ratings have so far only ever approved of. Something to use and something to learn from.

Timeline Studio

A video editor whose project file an agent can edit alongside you · Mac, in a Chromium browser

What it is. A local-first video editor that runs in the browser: a multi-track timeline, local AI voiceover, music, captions, repair and avatar features, and an export path it describes as deterministic and offline. The interesting part is the architecture. The editable .timeline project file is the source of truth, and an agent can propose a plan against it using stable clip IDs and timestamps, which you then review and apply. An agent can drive the open editor through 21 WebMCP tools, or work on the project file headlessly with npm run agent, including dry runs. There is a headless command runner — project.inspect, project.diff, project.run, project.render — and an Agent Skill packaged for Claude Code, Codex, Copilot and Gemini CLI.

Why it is for you. Your pipeline records HTML scenes with Playwright and hands the frames to ffmpeg. It works, and it is one-way: there is no editable artefact in the middle, so a change means re-running the generator and watching the output again. This project is the same problem solved from the other end — the timeline file is the artefact, and both you and Claude Code edit the same one. Use it for the children's music videos and the hymn videos, where local voiceover and captions are most of the work and currently the least automated part. Learn from it for one specific pattern worth stealing outright even if you never install it: stable clip IDs plus a proposed plan you apply, with project.diff and a dry run to inspect first. That is the difference between an agent that edits a video project and an agent that silently rewrites it, and it is exactly the guard-rail your own pipeline has no equivalent of.

To try it. git clone, npm install, npm run dev; it wants Node 20 or newer and a modern Chromium browser, and installs as a web app. The Agent Skill is a separate step (npx skills add … on Node 22.20+, or gh skill install …). Models are lazy-loaded from Hugging Face or ModelScope the first time you use a feature and then cached in the browser, so the first run of anything downloads. WebGPU is recommended for the heaviest AI work. An evening, and start by opening an existing clip rather than a real project.

Risk. 965 stars, 132 forks, created July 2026, pushed yesterday — comfortably the most active thing in this issue. The one number out of line is only 3 open issues for a project this size, which is not what a busy repository usually looks like; read the issue tracker before you trust it with work you care about. The licence needs reading properly: MIT covers the original source code only. Third-party models, weights, fonts, stock media and anything downloaded are explicitly not MIT and keep their upstream licences, voice models are a mix, and the project points you at its MODEL_LICENSES.md before you redistribute anything or use it commercially — which, for a YouTube channel, means read it first. On scope, be clear what is finished: headless rendering covers a documented subset only (visuals, voiceover and music to H.264/AAC MP4) and full headless render parity is listed as future work, so the agent cannot yet render everything the editor can. The roadmap is Now/Next/Later and there is no explicit beta label, which is a mild warning in itself. On data: the supported local workflows are described as not uploading your media to an editing backend, and no telemetry is mentioned — but there is a hosted editor and a Hugging Face Space, and an optional “Anna edition” that uses an account and cloud storage. Stay on the local path and that does not apply to you. Finally, worth knowing given the avatar ideas: the project restricts its deep-synthesis features to research and learning and to faces that are your own or authorised, which is its rule and a sensible one. ffmpeg is never named outright, though the headless importer uses ffprobe.

A game

No install, no login, and it works as well against the children as alone.

WikiSpeedrun

Race between two Wikipedia articles using only the links inside them · browser

What it is. You are given a starting article and a target, and you have to get there by clicking links inside the articles — no search box, no address bar. Solo, or in a shared room against other people. Three modes: Classic (first to the target), Tri (three targets in any order), and Marathon, new in version 1.0.0, which is a timed run of 3, 5, 8 or 12 minutes where the scoring rewards fewer clicks and pays bonuses at 5, 10 and 15 targets. The project's own summary: “no signup, no downloads, no ads”.

Why it is for you. It is the purest version of the ten-second game this section exists for: open a tab and you are playing, with nothing to install and nobody asking who you are. It also happens to be a genuinely good game to play with children — the shared rooms mean you can race them, and the skill it rewards is knowing how the world connects up, which is the history-and-general-knowledge instinct rather than reflexes. And there is a builder's reason too: the client is a single HTML file and the server is Node's plain http module with no framework and no dependencies at all. For someone who likes small shareable pages, that is a worked example of how little machinery a multiplayer browser game actually needs.

To try it. Open wikispeedrun.io and play. That is the whole instruction. To run your own copy it is Node 20 or newer, npm install, npm start, then localhost:3000.

Risk. MIT, stated in the LICENSE file. 166 stars, 21 forks, one open issue, created April 2026 and pushed yesterday — a healthy, unremarkable shape with no star anomaly to explain. Nothing is installed and there is no account, no API key and no database, so the risk here is mostly about what it touches: it calls Wikipedia directly — the client fetches article HTML from the REST API, the server checks your moves are legal against Wikipedia, and the puzzle pool is pre-generated from the pageview API. So your reading goes to Wikipedia, not to a third party, which is about as benign as it gets. No analytics are mentioned, though the server does log rejected moves on its own side. Three small things to know. Mobile and touch are addressed nowhere — it is a web page so it will almost certainly open on the iPad, but no device or browser is claimed, so treat that as untested rather than supported. The move-legality check deliberately fails open if Wikipedia errors, so an outage lets moves through unchecked — the right call for a game, worth knowing if you care about a clean score. And the puzzle pairs are pre-generated, so the pool is fixed until someone regenerates it. English Wikipedia only. There is a Ko-fi tip link towards hosting and API costs, which is a request, not a licence term.
