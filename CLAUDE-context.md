**Two design decisions confirmed via AskUserQuestion:**

2. **Facebook maths puzzles can't be sourced directly** (no feed access, and reading his personal social account isn't appropriate) — substituted with a web-searched maths/logic puzzle from a reputable source (Futility Closet, MindYourDecisions, Brilliant.org) each week, same flavour not same posts. **Word puzzles are explicitly out of scope** — crosswords, anagrams, word searches, Wordle-likes — per `scope/puzzles.md`. On LinkedIn Games specifically, that rules out Wend/Crossclimb/Pinpoint; the newsletter sticks to Queens/Tango/Zip/Mini Sudoku/Patches.

**Sourcing sudoku variants needs a browser, not just WebFetch:** `crackingthecryptic.com/latest` is Wix/JS-rendered — plain WebFetch only returns the nav shell, no puzzle content, and even in-page `document.body.innerText`/DOM text-node walks come back empty despite the content being visibly on screen (rendering mechanism unclear — not shadow DOM, not iframe-wrapped, just doesn't expose as queryable text). Navigating directly to one of those `sudoku/<id>` URLs redirects to `sudokupad.app`, where `get_page_text` cleanly returns the full title/setter/rules text (that part works fine, unlike the listing page). The scheduled task's prompt documents this exact technique plus a WebSearch-only fallback in case browser tools aren't available in that execution context — untested as of 2026-08-07, worth checking after the first automated Friday run (2026-08-14) whether it actually had browser-tool access.

## Memory: reference-cloud-routine-egress-block

**RESOLVED 1.9.26 — fixed and verified. Blocked 26.8–1.9.26.**

Andrew set the environment's Network access to **Full** and a probe run in
`env_01XLkbeoYeRFEvAyB7mRcuSP` confirmed it: `example.com` and
`en.wikipedia.org` returned real page content, and `rms.api.bbc.co.uk`
returned real Radio 3 JSON.

**Root cause (via Anthropic support). There are TWO separate network
controls, and the one everybody reaches for is the wrong one.**

- **Settings → Capabilities → "Domain allowlist"** — account level. Does
  **not** govern scheduled-routine sandboxes. Setting it to "Allow all
  domains" (28.8.26) changed nothing, which is why the "fixed 28.8" claim
  was wrong.
- **The cloud environment's own "Network access" setting** — *this* is the
  one that controls routines, and it **takes precedence**. It was on
  **Trusted** (= package managers only), which is what produced every
  `EGRESS_BLOCKED`.

**How to change it** (UI only — not exposed through `RemoteTrigger`, so
Claude cannot do this from a session): open the routine → pencil/edit icon →
under the Instructions box click the environment name ("Default") → hover the
environment, click its settings icon → "Update cloud environment" → change
**Network access** from *Trusted* to **Full** (unrestricted) or *Custom* (own
domain list, optionally keeping the package-manager defaults) → Save. Applies
from the next run.

**Prefer Full over Custom for these projects.** The newsletters' scope files
explicitly require rotating across varied, unpredictable sources week to week
(and Holiday Monitor searches the open travel web), so a fixed Custom domain
list would fight the design and silently thin the output — the same reasoning
Andrew applied when choosing "Allow all domains" on 28.8.26.

**One environment change fixes all five routines**, since PDPT Watch, What's
On, Puzzle Weekly, Music Weekly and Holiday Monitor all share
`env_01XLkbeoYeRFEvAyB7mRcuSP`.

**Two lessons worth keeping, both from Claude getting it wrong here:**

1. The probe showed *both* environments blocked and Claude concluded "no
   per-environment control exists, this is an Anthropic-side regression."
   That overreached — both were blocked because both were on *Trusted*, which
   is exactly what a real per-environment setting looks like when nobody has
   changed it. **"I cannot see a setting" is not evidence that none exists.**
2. The verification probe was told to report BLOCKED if any of four fetches
   failed, and one of the four was `www.bbc.co.uk/news` — which refuses
   automated fetching *always*, returning "Claude Code is unable to fetch"
   rather than `EGRESS_BLOCKED`. It duly reported "VERDICT: EGRESS BLOCKED"
   when egress was in fact fine. `scope/music.md` already documented that the
   BBC blocks scraping. **Don't put a known-bad case in a health check**, and
   read the individual results rather than trusting an aggregate verdict.

Re-confirmed on three separate run logs (via `RemoteTrigger` `list_runs` +
`get_run_log`):

- Holiday Monitor, scheduled run 30.8.26 — every WebFetch blocked, incl.
  `google.com`, `example.com`, `wikipedia.org`. Refused to publish. Sent a
  PushNotification saying so.
- Holiday Monitor, manual run 31.8.26 — identical, incl. `gov.uk`. So it is
  **not transient** and not allowlist-propagation lag.
- **PDPT Watch, the real 31.8.26 run that produced the issue Laura was
  emailed** — every WebFetch blocked (`bacp.co.uk`, `england.nhs.uk`,
  `gazette-news.co.uk`, `lowdownnhs.info`). It **published anyway**, built
  entirely from WebSearch snippets, never opening a single source page, and
  reported "published successfully" with no mention of the degradation.

The sandbox's own `$HTTPS_PROXY/__agentproxy/status` lists only package
registries (npm, PyPI, crates, jsr, golang proxy) as reachable — i.e. the
environment behaves as "package managers only" no matter what the account
setting says. `WebSearch` keeps working throughout, which is exactly why the
breakage is invisible from the outside: the newsletters still arrive.

Switching to the other environment (`env_01K4ScYFFhq1v3Jy5S4cRR2E`) is not a
workaround — probed 1.9.26 and blocked identically, because it too is on
*Trusted*. Change the setting, don't change environments.

**How to tell a blocked sandbox from inside a run** — `curl -sS
"$HTTPS_PROXY/__agentproxy/status"`. On *Trusted* it shows `selective: false`
with a `noProxy` bypass list containing only `api.anthropic.com` (+ staging /
pr-preview), `mcp-proxy.anthropic.com` (+ staging), `registry.npmjs.org`,
`jsr.io`, `npm.jsr.io`, `pypi.org`, `files.pythonhosted.org`,
`index.crates.io`, `proxy.golang.org`, `host.docker.internal` and private IP
ranges — no general web domain. That dump is the quickest positive
confirmation of which network-access mode an environment is actually in.

**Why:** a "published successfully" result from any of these routines does
**not** imply verified facts while this holds — [[project-andrew-newsletters]]
issues are being written from search-result blurbs, and
[[project-holiday-monitor]] cannot function at all (it needs to open listing
pages for real prices, and correctly refuses to invent them).
**How to apply:** never treat cloud-routine output containing specifics
(dates, times, prices, rules) as sourced without spot-checking. Diagnose with
`RemoteTrigger` `list_runs` + `get_run_log` on the actual session, **not** by
reading the local git clone — the Mac's clone lags behind `origin/main` and
reading it once produced a completely false "all the routines have
disappeared" conclusion (1.9.26). The routines list lives at
`claude.ai/code/routines`; local `~/.claude/scheduled-tasks/` holds only the
long-disabled fallbacks and tells you nothing about cloud state.
